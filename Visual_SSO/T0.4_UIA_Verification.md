# T0.4 — Does Chrome report `IsPassword` reliably?

**Status:** Not started
**Needs:** a Windows lab PC, Chrome, and one real DELIMa email address — **no password**
**Time:** an hour, most of it repetition
**Unblocks:** enabling `CheckUiaPasswordElement`, the field-identity layer of arch §4.2

`UiaHelper` and the gate in `RouteCLoginOrchestrator` are already built and fail closed correctly. They are switched off because nobody has measured whether Chrome actually reports the property. That is all this is.

---

## Part 0 — Why this is safer and cheaper than it sounds

**You never type a password.** Google's identifier page advances to the password page once it recognises a valid address, and recognising it is all you need. Enter a real DELIMa email, press Enter, land on the password page, sample what UIA reports, close the window. **No credential is ever typed, and no sign-in is ever completed.**

Three consequences worth knowing before you start:

- **No rate-limiting risk.** T0.2's timing test was capped at ten runs because each was a real sign-in. This is not, so 50 iterations is fine.
- **Nothing is stored.** T0.4 touches no credential store and raises none of the T0.1 questions.
- **A wrong or unknown address does not work.** Google will say *"Couldn't find your Google Account"* and never reach the password page. Use a real one — yours.

---

## Part 0.5 — Which machine

**The real run must be on a lab PC.** Not because the questions are exotic, but because two of the six are timing questions and timing is the whole point of using representative hardware:

- **Questions 1–4** — does UIA resolve an element, and does it report the right value — are largely Chrome's behaviour, and would likely give the same answer anywhere. *Likely* is doing work in that sentence; lab PCs often run an older or centrally-managed Chrome than a personal machine.
- **Questions 5–6** — how long the property takes to become readable, and whether forcing accessibility slows Chrome's start — are **meaningless off lab hardware.** A 4 GB spinning-disk PC is the machine a seven-year-old waits in front of, and question 5 feeds `injection_settle_ms`.

**Never over RDP.** Arch §11 already bans it for injection testing, and the reason applies doubly here: UIA and window focus are session-sensitive, and a remote session gives answers that do not transfer.

**Pick the slowest lab PC you have**, not a representative average. Timing requirements should be set by the machine that struggles.

**Smoke-test the probe anywhere first.** Run three iterations on whatever Windows machine is convenient, purely to confirm the probe launches Chrome, writes a CSV, and records something other than blanks. Discovering a bug in the tool while standing in the lab wastes the trip; the smoke-test results themselves are not evidence and should not be recorded as a run.

**You do not need the .NET SDK on the lab PC.** Publish the probe self-contained and single-file — the same flags as `Build_And_Release.md` §3 — and copy the one `.exe` to a pendrive. That is also a rehearsal of how `Delima.Provision` reaches those machines.

> **Expect antivirus interest.** Reading another process's accessibility tree is a technique credential stealers use, so endpoint protection may flag an unsigned probe doing exactly that. It is a false positive, and the same one anticipated for the unsigned installer in `Build_And_Release.md` §4.5. Do not respond by adding a permanent exclusion on a lab PC.

## Part 1 — Build the probe

The tool is small and observational. It does not automate the sign-in; you drive the browser by hand while it records what UI Automation sees.

Run **Prompt T0.4** in `Build_Prompts.md`. It produces a console probe that, once per 100 ms, writes a row containing:

| Column | Meaning |
| :--- | :--- |
| `elapsed_ms` | Since Chrome launched |
| `window_title` | Foreground window title, exactly |
| `focus_resolvable` | Did UIA return a focused element at all |
| `is_password` | What `IsPassword` reported, or blank if unresolvable |
| `run` | Iteration number |

---

## Part 2 — The procedure

**Launch Chrome through the probe, with `--force-renderer-accessibility`.** The probe does this itself. Verify the flag is actually being passed — without it Chrome exposes no accessibility tree and every row will read `focus_resolvable=false`, which looks like a failed test but is a mis-run.

Per iteration:

1. Probe launches Chrome at `https://d3.delima.edu.my/landing`
2. Click the sign-in button
3. Wait for the **identifier** page. Let it sit two seconds — the probe is sampling
4. Type your real email, press **Enter**
5. Wait for the **password** page. Let it sit two seconds
6. **Close the window. Do not type a password**
7. Probe records the run and relaunches

Fifty iterations. It is dull, and the dullness is the point — you are looking for the one run in fifty where the property is not there yet.

## Part 3 — Reading the result

Against the six questions in arch §11.1:

| # | Question | Pass condition | How to read it |
| :-- | :--- | :--- | :--- |
| 1 | Focused element resolvable on the identifier page? | ≥ 49/50 | Rows where title is the identifier title and `focus_resolvable=true` |
| 2 | `IsPassword == false` there? | **50/50** | Any `true` on the identifier page is a hard fail — it would mean typing an email into what the engine believes is a password box |
| 3 | Focused element resolvable on the password page? | ≥ 49/50 | Same, against the password title |
| 4 | `IsPassword == true` there? | **50/50, no tolerance** | See below |
| 5 | Time from page load to the property becoming readable | Record p50 and p95 | First row per page where `is_password` is populated, minus the row where the title changed |
| 6 | Does the accessibility flag slow Chrome's start? | Record | Compare `elapsed_ms` to first title, with and without the flag |

**Question 4 admits no failures, and it is worth being clear why.** Every other check in this product degrades into an abort and a retry — annoying, recoverable, a pupil sees an error. A false negative on question 4 means the engine believes the caret is not in a password field when it is; it aborts, which is safe. A **false positive** — `true` when the caret is somewhere else — is a password typed into a visible field in a room full of children. If any run reports `is_password=true` on a page that is not the password page, stop and re-plan §4.2. Do not average it away.

**Question 5 feeds `injection_settle_ms`.** If the property takes longer to appear than the current 400 ms default, raise the default rather than lowering the requirement.

## Part 4 — What to do with the answer

**If questions 1–4 pass:** set `CheckUiaPasswordElement` to `true` by default in `RouteCLoginOrchestrator`, record the result here and in arch §11.1, and the field-identity layer of §4.2 is live. Titles then become the first gate and `IsPassword` the second, which is what removes the locale and redesign risk titles carry on their own.

**If question 1 or 3 fails** — UIA often cannot resolve a focused element — the gate would abort valid sign-ins. Leave it off, record why, and either investigate the accessibility flag or fall back to `--remote-debugging-pipe` and CDP per §4.2. **Never `--remote-debugging-port`.**

**If question 2 or 4 fails**, the property is not trustworthy on this hardware and §4.2's field layer cannot be built on it. Titles remain the only gate, which makes the Malay-locale capture and the exact-match discipline more load-bearing, not less.

**Either way, record the result.** A measured "it does not work here" is worth as much as a pass — it stops the next person assuming the inert gate is active, which is the state the code was in until it was caught.

### Methodology note — read before citing these numbers

**100 runs were started; 49 reached the password page.** The operator closed the remaining runs early because fifty full iterations is tedious. Per Part 3, incomplete runs are excluded from the denominator rather than scored as failures, so Q4 reads **49/49 — a 100% rate**, not 49/100.

**The caveat this creates, stated plainly.** If runs were abandoned *because a page felt slow*, the sample is biased toward fast ones, and the p95 of 417 ms is optimistic — which matters, because that figure set `injection_settle_ms`. The operator reports abandoning them out of tedium rather than because anything looked wrong, which suggests the bias is small. **700 ms was chosen to leave headroom over the measured max of 434 ms rather than to sit just above p95**, precisely because of this uncertainty.

**If Q5 is ever re-measured, do it on completed runs only**, and note that fifty is more than the question needs. Twenty completed runs would answer Q1–Q5 with adequate confidence and are far likelier to actually be completed.

### The two findings that changed the spec

Neither was the question T0.4 set out to answer, and both would have broken the product.

**1. The identifier title in Appendix B was wrong.** T0.2 recorded `Sign in - Google Accounts - Google`; the actual string is `Sign in - Google Accounts - Google Chrome`. Exact matching would have failed 100% of the time. Corrected.

**2. The password page has no fixed title.** It shows `Welcome - Google Chrome` briefly, then `Hi <ACCOUNT HOLDER NAME> - Google Chrome` — **it contains the pupil's own name**, so no configured constant can match it. This is why the UIA result matters more than expected: arch §4.2 now makes `IsPassword` the primary gate for the password step, with the title reduced to a sequence-and-stability check there. The identifier step keeps exact matching, since its title is fixed.
