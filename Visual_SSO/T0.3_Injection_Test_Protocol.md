**Purpose:** decide whether the DELIMa Smart Launcher is buildable at all.
**Owner:** King
**Where:** a representative lab PC at SK Seksyen 24. Not a developer machine.
**Time:** ~2 hours in the lab, plus ~1 hour of preparation the day before.
**Companion:** `PRD_Visual_SSO_v2.md` §2, `Technical_Architecture_Visual_SSO.md` §4.
**Status: PASSED, 17 August 2026.** See "Actual results" at the end of this document. T0.3 no longer blocks the programme — T0.1 (written policy position) is now the active blocker.

Print this. You will be standing at a lab PC with your hands off the keyboard for long stretches.

## 0. The decision this test makes

| Outcome | What it means | What you do |
| :--- | :--- | :--- |
| `sendinput` clean sweep, `sendkeys` corrupts reserved characters | Expected. Injection is viable; `SendKeys` would have silently broken every pupil whose password contains `+ ^ % ~ ( ) { } [ ]`. | Proceed to Phase 1. Record the finding — it justifies the whole v2 rewrite. |

## 1. Rules

These are not ceremony. The harness drives the real keyboard.

1. **Synthetic passwords only.** The built-in test set is fake. Never point Mode A at a real account, never edit a real pupil password into `TestPasswords`.
2. **Not over Remote Desktop.** `SendInput` targets the physical input queue and `BlockInput` behaves differently in an RDP session. Sit at the machine.
3. **Do not leave the desk mid-run.** If `BlockInput` is denied, your keystrokes and the harness's interleave, and the run is garbage.
4. **Nothing else open.** No Word document, no browser with a form, no chat window. If window verification fails and something goes wrong, keystrokes land wherever focus is.
5. **Close your own Chrome first**, and check afterwards that it survived — teardown correctness is one of the things being tested.
6. **Mode B touches Google.** It sends no keystrokes and needs no account, but it does make 50 requests from the school IP. Run it once, not repeatedly.

## 2. The day before — build it on your machine

The spike has **never been compiled** (`InjectionSpike/README.md`). Expect trivia. Fix it at your desk, not in the lab with 40 minutes of access.

```powershell
cd InjectionSpike
dotnet build -c Release
```

Then smoke-test with a tiny run so you arrive knowing it works:

```powershell
dotnet run -c Release -- fidelity --method sendinput --runs 3
```

Watch for: Chrome resolving from the registry, a window appearing, the verdict landing. Three runs is enough to prove the machinery; it proves nothing about lab hardware.

**Things worth checking while you are here:**

- `Microsoft.Win32.Registry` resolves on `net10.0-windows` without an extra package reference. If not, add it.
- `Marshal.SizeOf<INPUT>()` should be **40** on x64. Print it once if a run behaves oddly — a wrong struct size makes `SendInput` return 0 and inject nothing.
- If `BlockInput` returns false, you are not elevated. Note it; do not fix it by running as admin, because production will not be elevated either.

### 2.1 Replace the test password set with real *shapes*

`TestPasswords` in `Program.cs` is a guess about what MOE passwords look like. Before the lab session, ask the ICT coordinator what the actual generated pattern is — length, whether symbols appear at all, which ones.

**Ask for the pattern, never the passwords.** If real MOE passwords turn out to be `Murid1234` with no symbols, half this test is theatre and you should know that before you build a warning system (wizard Step 4) around characters that never occur. If they do contain symbols, add the real shapes to the list.

## 3. In the lab

### Step 1 — Baseline the machine

Record before you start: PC model, CPU, RAM, **disk type (HDD or SSD — this is the single biggest factor in Mode B)**, Windows build, Chrome version, screen resolution, and whether it is on Wi-Fi or wired.

A result without this context cannot be generalised to the other 39 PCs.

### Step 2 — Mode A, `sendkeys` (the control)

```powershell
dotnet run -c Release -- fidelity --method sendkeys --runs 50
```

~8 minutes. **Run the control first.** If you run `sendinput` first and it passes, you will be tempted to skip this — and then you have no evidence for the claim the rewrite rests on.

Expected: plain rows pass, reserved-character rows fail.

### Step 3 — Mode A, `sendinput` (the candidate)

```powershell
dotnet run -c Release -- fidelity --method sendinput --runs 50
```

Expected: clean sweep.

**If any row fails, do not conclude the method is broken yet.** Re-run that case with a per-character gap:

```powershell
dotnet run -c Release -- fidelity --method sendinput --runs 20 --char-delay 15
```

Fast injection dropping characters is a different fault from character *corruption*, and it has a cheap fix. Whichever `--char-delay` produces a clean sweep becomes the production value in `injection_settle_ms`'s sibling setting. `0` is preferred; do not raise it without evidence.

### Step 4 — Mode B, timing, **cold**

This is the number that kills the PRD's 1,500 ms sleep, and it is the one most easily measured wrong.

**Reboot the PC. Log in. Wait for the disk to settle. Then run exactly one iteration:**

```powershell
dotnet run -c Release -- timing --runs 1
```

Record it. **Repeat the reboot 5 times.** Those five numbers are your only true cold-start data.

Why the ceremony: after the first launch, Chrome's binaries sit in the OS file cache, so runs 2–50 are warm and materially faster. The condition you actually care about is the first pupil of the day on a cold machine — the case the harness's default 50-run loop measures exactly once and then averages away.

### Step 5 — Mode B, timing, warm

```powershell
dotnet run -c Release -- timing --runs 50
```

~12 minutes. This gives you the steady-state distribution for pupils 2 through 30, which is the common case. Report cold and warm **separately**. A single blended p50 describes a situation that never occurs.

### Step 6 — The adversarial test (manual, and the one that matters most)

Modes A and B prove injection works. This proves it **refuses to work when it shouldn't** — the test that stands between a child's password and the URL bar.

1. Open Notepad. Leave it visible.
2. Start a fidelity run.
3. While the harness is waiting for its window, **click on Notepad** to steal focus.
4. Wait for the run to complete.

**Pass:** the run reports `WINDOW_NOT_READY`, and **Notepad is empty.**
**Fail:** any character appears in Notepad. If that happens, stop the programme and fix window verification before anything else.

Repeat 5 times, stealing focus at different moments — immediately, at ~1 s, ~2 s, ~4 s.

Also confirm, at the end of the whole session: **your own Chrome is still open and did not prompt "Restore pages?"**, and `%TEMP%` contains no leftover `delima_spike_*` directories.

## 5. What 50 runs can and cannot tell you

The PRD's exit criterion says *"injection success ≥ 99% over 50 runs"*. **50 runs cannot demonstrate 99%.** Fifty consecutive successes bounds the true failure rate at roughly 6% with 95% confidence — nowhere near 1%. Certifying 99% would take ~300 clean runs.

That is not a reason to run 300. It is a reason to be clear about what each phase buys:

- **T0.3 (50 runs)** detects *gross, deterministic* failure — which is exactly what `SendKeys` character corruption is. It answers "is this approach broken?", and that is the question blocking everything.
- **The pilot (Phase 5)** produces the real reliability figure, from hundreds of genuine sign-ins across many PCs, logged by the app.

Amend the PRD exit criterion to *"zero unexplained failures across 50 runs, with `sendkeys` corruption reproduced as the control"*, and move the 99% target to the pilot where it can actually be measured.

## 6. Known limitations of this harness

State these alongside the results, or someone will over-read them.

1. **Mode B measures window-title match, not password-field readiness.** The real target is when the field is focused and accepting input; the title appears earlier. Treat Mode B's numbers as a **lower bound** on the true wait.
2. **Mode A uses a local `file://` page.** No network, no SAML redirect, no Google page weight. Real latency will be worse; real *fidelity* should be identical, which is the point of isolating it.
3. **One machine is not a lab.** Run at least Steps 3 and 6 on a second PC of a different age before trusting the result across 40.
4. **The title predicate is locale-dependent.** Mode B matches "Google", "Sign in", "Log masuk", "DELIMa". If the lab's Chrome is in a different language, it will time out and look like a failure that isn't.
5. **`--char-delay` was added for this protocol** and is untested in anger. If it behaves oddly, `0` is the original path.

## Appendix — the patch applied before this protocol was written

Two changes were made to the harness so its results can be trusted:

**`testpage.html` — debounced the verdict.** `input` fires per character, so the window title previously passed through `SPIKE:FAIL:LEN_1_OF_19`, `LEN_2_OF_19`… on its way to the truth. The harness polls every 100 ms and could sample one of those, recording a FAIL for a run that succeeded. The bias pointed the wrong way: longer strings dwell longer in the intermediate state, and the longest strings in the set are the reserved-character ones — so an undebounced harness fails `sendinput` on precisely the passwords `sendkeys` is expected to fail on, and the whole run reads as "injection is impossible". A 400 ms settle window plus an intermediate `SPIKE:TYPING` title fixes it.

**`Program.cs` — added `--char-delay`.** Separates *dropped* characters from *corrupted* ones. They look identical in the summary and have completely different fixes.

Two further patches followed real lab runs, each traced to a specific uploaded CSV rather than guessed:

**`Program.cs` — guaranteed run-order coverage.** The original `perPassword = runs / TestPasswords.Length + 1` distribution, combined with the outer loop stopping the instant `results.Count` hit the requested run count, silently dropped whichever passwords sorted last whenever the arithmetic didn't divide evenly. At `--runs 50` against 12 passwords that meant `all-reserved` and `moe-style` — the two most informative cases — never ran, with nothing in the output saying so. Replaced with an explicit run order that places one of every password before any repeats.

**`Program.cs` and `--method` validation.** A misspelled `--method sendkets` (or `sendinputs`) fell through the old `if (method == "sendkeys") ... else sendinput` dispatch and silently ran `SendInput` under a filename that read as the opposite method's control run. The tool now refuses to run `fidelity` mode unless `--method` is exactly `sendkeys` or `sendinput`.

**`Program.cs` and `NativeMethods.cs` — stale-window cleanup.** A run following an earlier interrupted attempt (crashed build, closed PowerShell mid-run) could find a leftover Chrome window still carrying the `SPIKE:` title prefix. The next run's window-verification wait could then latch onto that old window instead of the new one it had just launched — the signature was ~45% of runs reporting `NO_VERDICT_TIMEOUT` and one run's window-ready time spiking to 15.6 s against ~650 ms for the rest. `Program.cs` now closes any window matching that prefix at the start of every invocation, via a new `NativeMethods.CloseWindowsWithTitlePrefix()`.

**`Program.cs` — caught the `SendKeys` crash.** For the `braces` password (`Murid{2026}`), `SendKeys.SendWait` doesn't merely mistype — it throws `ArgumentException: Keyword "2026" is not valid`, because `{` opens keyword syntax and `2026` isn't a recognised keyword. Uncaught, this took the whole batch down before the CSV was written, losing every result measured before the crash. The injection call is now wrapped in `try`/`catch`, recording `SENDKEYS_THREW: ...` as a `FAIL` row and continuing through the rest of the passwords. This finding stands on its own merits: a real MOE password containing `{` would have crashed the v1 launcher outright, not merely logged the wrong pupil in.

**Verdict: PASSED.** `SendInput` is viable. T0.3 no longer blocks; T0.1 is now the active item.

| 2 | `fidelity_sendinput_d0_20260817_175502.csv` | sendinput | **50/50 passed.** No anomalies. |

| 4 | `fidelity_sendkeys_d0_20260817_180524.csv` | sendkeys | **Anomalous — 0/50 excluding the one `braces` crash.** Even the plain passwords failed with `NO_VERDICT_TIMEOUT`, ~14 minutes after batch 3 on the same machine. **100/100 for `sendinput` across two independent batches**, including `all-reserved` (every reserved character combined into one password) and `moe-style` (the realistic shape). Zero failures, zero exceptions. `Technical_Architecture_Visual_SSO.md` §4.3 updated: the injectable-character-set warning planned for the wizard's Step 4 has been removed rather than tuned, since there is no character class found to cause a problem.

**Test 5 (adversarial focus-steal) — 2 of 5 attempts completed, both clean, plus one important unplanned finding.** Stealing focus at the 1 s and 3 s marks — before injection began — produced zero leaked keystrokes both times: window verification is working as designed. Three more pre-injection attempts (at ~0 s, ~2 s, ~4 s) are needed to complete the protocol's full 5/5, though the mechanism is already well understood and this is not treated as blocking.

Separately, and not originally specified in this protocol: stealing focus **during** active injection (after typing had started) did leak characters into the stolen window. This is not a failure of window verification — it is a different, real gap, and it is now understood rather than surprising. Every successful run in all four CSVs above shows `blockinput_denied`: `BlockInput()` returned `false` on every single call, meaning nothing was actually locking the keyboard during injection on this hardware. The Launcher will not run elevated on a shared pupil account in production either, so this is the **normal case**, not a hardware quirk of this one PC. `Technical_Architecture_Visual_SSO.md` §4.2 has been updated accordingly: the topmost-overlay fallback for when `BlockInput` is denied is now stated as **required for every standard deployment**, not a contingency for unusual images. This lab result is the reason why.

**Machine.** Both machines seen so far are `PEP-BBA8105-15` (the first session) and `PEP-BBA8105-18` (this session) — different lab PCs, which happens to satisfy the "second machine of a different age" check in §6 even though it wasn't deliberately arranged. Disk type, RAM, and Chrome version for `PEP-BBA8105-18` were not recorded — worth capturing per §7.1 if a further batch is run on it. Mode B (timing) has only been run on `PEP-BBA8105-15`; repeating it on `-18` would be useful but is not required for this verdict, which concerns fidelity, not latency.
