## Observed flow — August 2026

Captured by walking the live portal. Session-bound values (`state`, `dsh`, `as`, `part`) are deliberately replaced with placeholders here — they are single-use and expired, but this repository is public and there is no reason to publish session tokens.

**1. Landing**

```
https://d3.delima.edu.my/landing
```

**2. Redirects into a Google OAuth 2.0 authorization-code flow**, with DELIMa's own OAuth client:

```
https://accounts.google.com/v3/signin/accountchooser
  ?client_id=950472034074-acj262jqk6trve8i4ndsudqeokvh5pef.apps.googleusercontent.com
  &redirect_uri=https%3A%2F%2Fd3.delima.edu.my%2Fauthentication%2Fcode
  &response_type=code
  &scope=openid+email+profile
  &state=<server-generated, validated on callback>
  &dsh=<session>  &o2v=2  &service=lso  &flowName=GeneralOAuthFlow
  &app_domain=https%3A%2F%2Fd3.delima.edu.my
```

**3. Then the identifier (email) page**, carrying the same parameters:

```
https://accounts.google.com/v3/signin/identifier?...same client_id, state, dsh...
```

**The canonical authorize request**, captured from the Network panel — this is what DELIMa actually constructs, before Google's internal rewrites:

```
https://accounts.google.com/o/oauth2/v2/auth
  ?scope=openid%20email%20profile
  &state=<server-generated, single-use>
  &response_type=code
  &redirect_uri=https%3A%2F%2Fd3.delima.edu.my%2Fauthentication%2Fcode
  &client_id=950472034074-acj262jqk6trve8i4ndsudqeokvh5pef.apps.googleusercontent.com
```

**Five parameters, and two notable absences:**

- **No `login_hint`.** DELIMa does not send one today. This makes the row above the test instrument for 3A: if DELIMa forwards a hint, it appears here.
- **No `hd`.** `Normal_SSO` §5.2 uses `hd=<domain>` to suppress consumer Google accounts in the picker. DELIMa does not, so a personal Google account signed into the same browser can appear as an option. Moot on a throwaway profile, relevant on a teacher's own machine.

`response_type=code` confirms an authorization-code flow, meaning DELIMa's server exchanges the code using a client secret it alone holds — another reason the launcher cannot construct its own valid flow.

### What this settles

- **Q1 is answered. It is Google OAuth 2.0.** Arch §4.5's core assumption holds — this is not a proprietary identity provider, and the section does not need re-specifying at the root.
- **DELIMa runs its own Google Cloud project.** The `client_id` above is DELIMa's. **No school Cloud project is needed**, which removes the cost that made the `login_hint` route look expensive. A `client_id` is not a secret; it is visible to every user in every authorize URL. DELIMa's *client secret* is a different matter and must never appear here.
- **`state` blocks the obvious approach.** It is generated per session by DELIMa and validated when Google calls back. The launcher cannot mint its own authorize URL with `login_hint` appended — an invented `state` fails validation, leaving the pupil signed into Google but not into DELIMa.

## Part 2 — The clean-profile rule

**This is the part people get wrong, and getting it wrong produces a confident false result.**

If you are already signed into Google in your normal browser, the sign-in pages behave completely differently — Google skips the identifier step entirely because it already knows who you are. You will conclude the pre-fill works beautifully when in fact you never tested it.

So every test runs in a **fresh, throwaway Chrome profile**, which is also exactly how the product will launch Chrome (arch §4.4). Step 1.3 below sets up a `New-TestChrome` shortcut that does this for you — use it for every test rather than opening Chrome normally.

When a test window opens it should look freshly installed: no bookmarks, no profile picture, no "Welcome back". **If it looks like your normal browser, stop** — the profile flag did not take effect and every result after that is meaningless.

### Doing all of it in one session on a school laptop

Simplest approach, and the most representative — everything runs on the network and hardware the product will actually meet. About an hour, plus setup if you want step 5.

**Have ready before you sit down:**

- Your own DELIMa account and password — not a pupil's

- A text file open for pasting results


### Step 1 — Set up

**1.1** Close **every** Chrome window. Check none are hiding in the system tray. This matters for step 4, where you read window titles and stray windows make the list ambiguous.

**1.2** Open a terminal. On Windows: press the Windows key, type `powershell`, press Enter. On macOS: open **Terminal** from Applications → Utilities.

**1.3** Define a shortcut you will reuse for every test. It launches Chrome in a brand-new empty profile each time, so you are never accidentally testing an already-signed-in session.

**On Windows (PowerShell):**

```powershell
function New-TestChrome($url) {
  $p = "$env:TEMP\t02-" + (Get-Date -Format "HHmmss")
  Start-Process "C:\Program Files\Google\Chrome\Application\chrome.exe" `
    -ArgumentList "--user-data-dir=`"$p`"", "--no-first-run",
                  "--no-default-browser-check", "--new-window", $url
}
```

**`Start-Process`, not `&`.** Launching Chrome with `&` blocks the prompt until Chrome closes, and step 4 requires running commands while a Chrome window is still open.

**`--no-first-run` and `--no-default-browser-check`** suppress Chrome's welcome screens. Without them every fresh profile opens with "Sign in to Chrome" and "Make Chrome your default", which get in the way once you are launching a window per test.

> ### The two sign-ins, which are not the same thing
>
> This trips people up, and getting it wrong invalidates the whole session.
>
> | Prompt | What it is | What to do |
> | :--- | :--- | :--- |
> | **"Sign in to Chrome"**, "Turn on sync", a profile picture in the corner | The **browser** offering to sync bookmarks and history to a Google account | **Always skip.** "No thanks", "Continue without an account", or close it. Signing in here pollutes the throwaway profile and makes every later result meaningless. |
> | **"Sign in with Google"** on the DELIMa page, or a Google page asking for an email and password | The **OAuth flow you are testing** | **Sign in normally.** This is the test. |
>
> If you have already signed into Chrome itself in a test profile, close that window, delete the profile folder, and start the test again.

If Chrome is installed elsewhere, correct the path — find it with `Get-ChildItem "C:\Program Files*\Google\Chrome\Application\chrome.exe"`.

**What you should see when you paste this: nothing.** Defining a function produces no output. PowerShell will show `>>` while you paste the multi-line block — press **Enter on an empty line** to finish it. Confirm it registered with:

```powershell
Get-Command New-TestChrome
```

**On macOS (Terminal)** — for steps 1–3 only; step 4 needs Windows:

```bash
newchrome() {
  "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
    --user-data-dir="/tmp/t02-$(date +%H%M%S)" --new-window "$1" &

```

**1.4** Test the shortcut — `New-TestChrome "https://www.google.com"` on Windows, `newchrome "https://www.google.com"` on macOS.

**What should happen:** a Chrome window opens within a few seconds, and **your prompt comes straight back** — you can keep typing while Chrome is open.

**What a fresh profile looks like:**

| Sign | Meaning |
| :--- | :--- |
| A "Welcome to Chrome", "Sign in to Chrome" or "make Chrome default" dialog | **Good** — it proves the profile is genuinely new. **Skip it, never sign in.** With `--no-first-run` it should not appear at all. |
| No bookmarks bar, no bookmarks | Good |
| No profile picture top-right; google.com shows a **Sign in** button | Good — you are not signed in, which is the point |
| Your bookmarks, your account, "Welcome back" | **Stop.** The profile flag did not take effect |

**If it looks like your normal Chrome, fix it before going further** — every result after this point would be meaningless. Usual causes: Chrome was still running (close every window, check the system tray), or the path in the function is wrong.

**If nothing opens at all**, the Chrome path is wrong. Run `Get-ChildItem "C:\Program Files*\Google\Chrome\Application\chrome.exe"` and use whatever it prints.

**2.3 — Reading it out of DevTools.**

**What you are hunting for, in one sentence:** the **last address on `d3.delima.edu.my` before the browser jumps to `accounts.google.com`.** That is the URL that starts the login, and it is what step 3 attaches `login_hint` to.

**Set up:**

1. Press **F12**. A panel opens, usually on the right or bottom.
2. Click the **Network** tab along the top of that panel.
3. Tick **Preserve log**. This matters — without it the list is wiped the moment the page redirects, which is exactly when you need it.
4. Click **Doc** in the row of filter buttons (`All | Doc | Fetch/XHR | JS | CSS | Img | ...`). This hides images, scripts and stylesheets, leaving only page navigations. **Without this filter you will be looking at 200 rows instead of about 5.**

**Now click the sign-in button on the page.**

**What appears.** A short list, roughly like this — the columns are Name, Status, Type, Initiator:

```
Name                          Status    Type
────────────────────────────────────────────────
landing                       200       document      ← the page you started on
login                         302       document      ← what you want
accountchooser?client_id=...  200       document      ← Google, too late
```

**How to spot the right row:**

| Look for | Meaning |
| :--- | :--- |
| Status **302** or **307** | A redirect. The login-start URL is almost always one of these. |
| The **last** row still on `d3.delima.edu.my` | Everything after it is Google. That boundary is the answer. |
| Names like `login`, `signin`, `auth`, `oauth2`, `google` | Typical, but do not rely on the name — rely on the domain boundary. |

Hover a row to see its full URL, or click it and read **Request URL** at the top of the **Headers** tab on the right. Right-click the row → **Copy** → **Copy link address** gets it onto the clipboard.

**Write down:** that URL. Probably something like `https://d3.delima.edu.my/login` or `.../auth/google`.

---

**If you cannot find it, do not get stuck here.** Use `https://d3.delima.edu.my/landing` for step 3 and note in your results that the login-start URL was not identified. Test 3A may then give a false negative — if `/landing` only renders a page with a button, a parameter added to it gets dropped when the button is clicked. That is worth knowing when you read the result, and it is a much better outcome than abandoning the session.

### Step 3 — Test whether a pre-fill works

Substitute your own address for `m-12345678@moe-dl.edu.my` everywhere below.

#### Test 3A — Does DELIMa forward `login_hint`?

**What this test is asking.** Google's sign-in accepts a parameter called `login_hint` that pre-fills the email box. The launcher cannot call Google directly, because the authorize URL needs a `state` value only DELIMa's server can generate. So the question is narrower: **if you put `login_hint` on DELIMa's own URL, does DELIMa copy it into the Google URL it builds?** Many OpenID Connect libraries forward it automatically. Some ignore it. Nobody knows which DELIMa does until you try.

**Which URL to attach it to.** Use `https://d3.delima.edu.my/landing` unless step 2 gave you something better. That is the normal case and it is sufficient — the check below reads DELIMa's authorize request directly, so it works whether the redirect happens on DELIMa's server or in its JavaScript.

**Never attach it to a captured `accounts.google.com` URL.** Those carry `state`, `dsh`, `part` and `rart` values that are single-use and session-bound. Testing there either fails for reasons unrelated to `login_hint`, or appears to succeed in a way that can never be shipped — the launcher cannot mint any of those values.

**Building the test URL. One rule:**

> **Does your URL already contain a `?`** — **yes:** join with `&`. **No:** join with `?`.

```
The normal case — no ? yet, so join with ?
  https://d3.delima.edu.my/landing
  → https://d3.delima.edu.my/landing?login_hint=m-12345678@moe-dl.edu.my

If step 2 gave you a URL that already has parameters, join with &
  https://d3.delima.edu.my/login?redirect=%2Fdashboard&lang=ms
  → https://d3.delima.edu.my/login?redirect=%2Fdashboard&lang=ms&login_hint=m-12345678@moe-dl.edu.my
```

**Always add it at the very end**, and **always keep the whole thing inside double quotes** — a URL containing `&` will break if unquoted in PowerShell.

```powershell
New-TestChrome "https://d3.delima.edu.my/landing?login_hint=m-12345678@moe-dl.edu.my"
```

**Then click the sign-in button on the page.** The hint has to survive whatever DELIMa does next, which is the entire point of the test.

**Then read the result — from the Network panel, not the address bar.**

After the redirect the address bar shows Google's internal `v3/signin/...` rewrite, which is not the request DELIMa built. The reliable place to look is the same row you found in step 2.3:

1. Keep DevTools open with **Preserve log** ticked and the **Doc** filter on
2. Find the `accounts.google.com/o/oauth2/v2/auth?...` row
3. Copy its URL and search that text for `login_hint`

That row is DELIMa's authorize request verbatim. Today it carries five parameters and no hint (see "Observed flow" above), so **if `login_hint` appears there, DELIMa forwarded it — that is the whole answer.**

**Reading the result:**

| What you see in the `o/oauth2/v2/auth` row | Meaning | Next |
| :--- | :--- | :--- |
| `login_hint=` present **and** a password field with the email filled in | **Best case.** Route A works. | Record the URL; 3B and 3C not needed |
| `login_hint=` present, but still an empty email box | DELIMa forwarded it; Google ignored it — often a domain or account mismatch | Note it, then try 3B |
| Still the same five parameters, no `login_hint` | DELIMa dropped it | Retry with `hint=` then `email=`; if neither survives, go to 3B |

**Write down:** which parameter name survived if any, whether the email was pre-filled, and the final URL with your email replaced by `<email>`.

Close the window.

#### Test 3B — Account chooser first (only if 3A failed)

Sign in when prompted. **The question is what happens after the password step** — does DELIMa complete on its own, or does it ask you to pick an account again?

**Write down:** whether the email was pre-filled at the Google step, and whether DELIMa completed without further prompting.

Close the window.

### Step 4 — Capture the window titles (do not skip)

Arch §4.2 checks the window title before sending any keystroke. You need a string that appears on the **password screen only**. The spike already lost a run to this: it matched a fragment present in every Chrome window and reported a false ready state in 47 of 50 runs.

**4.1** Get to the sign-in flow again with whichever URL worked best:

```powershell
New-TestChrome "https://d3.delima.edu.my/landing"
```

**4.2** At **each** of the stages below, leave the window open, switch to PowerShell, and run:

```powershell
Get-Process chrome | Where-Object { $_.MainWindowTitle -ne "" } |
  Select-Object -ExpandProperty MainWindowTitle
```

Capture the title at all five stages:

| # | Stage | Title (copy exactly) |
| :-- | :--- | :--- |
| 1 | Page still loading | |
| 2 | Account chooser, if one appears | |
| 3 | **Email / identifier field showing** | |
| 4 | **Password field showing** | |
| 5 | Signed in, on DELIMa | |

**Rows 3 and 4 are both required if route C is in play** — that is, if no pre-fill route worked and the launcher must type the email as well as the password. Each injection needs its own window check (arch §4.2), so each page needs its own identifying string, and **the two must be distinguishable from each other**. If the identifier and password pages share a title, the engine cannot tell which step it is on, and §4.2 needs a second signal.

**Copy them character for character** — including the ` - Google Chrome` suffix and any leading account name. "Roughly what it said" is not usable for a string match.

**4.3** Now compare them and answer these:

> **Q1. Is there text that appears in row 4 (password) and in none of the other rows?**
>
> **Q2. If route C applies — text that appears in row 3 (identifier) and no other row, including row 4?**

- **Both yes** → those strings are what arch §4.2 matches on. Write them down. This is the deliverable.
- **Either no** → a real finding. Window verification needs a different signal — window class, or reading the tab URL — and **arch §4.2 must be revised before build step 11.** Record all five titles so the decision can be made from evidence rather than guesswork.

**Do not skip Q2 on the assumption that route B will work.** If it does not, the launcher types the email first, and an engine that cannot tell the identifier page from the password page could type a password into the email box — in plain text, on screen, in a room full of children.

## Part 8 — What each outcome means

| Outcome | What it means | What to do |
| :--- | :--- | :--- |
| **B1 works** — `login_hint` passes through, password field pre-filled | Best case. One injection, no picker. | Record the URL, unblock Prompt 11 |
| **B2 works** — chooser signs in, DELIMa completes on its own | Good. One extra page, still one password injection. | Record it; note the extra step in the pupil guide |
| **B3 only** — no pre-fill available | Acceptable. Two injections, both proven at T0.3. | Build §4.2's engine for a two-step sequence |
| Account picker appears despite `hd` | One extra pupil click; does not break the product | Record it; the pupil-facing guide must show that screen |

**`DELIMa does not use Google sign-in` has been removed from this table — it was the outcome that would have forced a respec, and the August 2026 observation ruled it out.**

**The window-title row is now the one carrying real risk.** It would otherwise surface midway through building the injection flow, which is the most delicate code in the product.

**Design for route C regardless of what passes.** Even if B1 works today, Google changes these flows without notice, and an engine that can only handle a pre-filled email will break on the day it stops being pre-filled. Two-step capability is the resilient design, not the fallback.

## A note on doing this safely

You are typing a real password into a real sign-in page, which is ordinary. Two things to keep ordinary:

- **Do not save the password in Chrome.** Decline the prompt. The throwaway profiles are deleted afterwards anyway, but decline it regardless.
- **Do not run these tests on a pupil's account without the school's knowledge.** Your own account, or an account created for testing, avoids the question entirely.

Nothing in T0.2 stores a credential, and nothing here engages the T0.1 question — this is an ordinary sign-in, not storage or replay.
