## Observed flow — August 2026

Captured by walking the live portal. Session-bound values (`state`, `dsh`, `as`, `part`) are deliberately replaced with placeholders here — they are single-use and expired, but this repository is public and there is no reason to publish session tokens.

**1. Landing**

```
https://d3.delima.edu.my/landing
```

**2. Redirects into a Google OAuth 2.0 authorization-code flow**, with DELIMa's own OAuth client:

```
https://accounts.google.com/v3/signin/accountchooser
  ?client_id=950472034074-acj262jqk6trve8i4ndsudqeokvh5pef.apps.googleusercontent.com
  &redirect_uri=https%3A%2F%2Fd3.delima.edu.my%2Fauthentication%2Fcode
  &response_type=code
  &scope=openid+email+profile
  &state=<server-generated, validated on callback>
  &dsh=<session>  &o2v=2  &service=lso  &flowName=GeneralOAuthFlow
  &app_domain=https%3A%2F%2Fd3.delima.edu.my
```

**3. Then the identifier (email) page**, carrying the same parameters:

```
https://accounts.google.com/v3/signin/identifier?...same client_id, state, dsh...
```

### What this settles

- **Q1 is answered. It is Google OAuth 2.0.** Arch §4.5's core assumption holds — this is not a proprietary identity provider, and the section does not need re-specifying at the root.
- **DELIMa runs its own Google Cloud project.** The `client_id` above is DELIMa's. **No school Cloud project is needed**, which removes the cost that made the `login_hint` route look expensive. A `client_id` is not a secret; it is visible to every user in every authorize URL. DELIMa's *client secret* is a different matter and must never appear here.
- **`state` blocks the obvious approach.** It is generated per session by DELIMa and validated when Google calls back. The launcher cannot mint its own authorize URL with `login_hint` appended — an invented `state` fails validation, leaving the pupil signed into Google but not into DELIMa.

## Part 0 — What you are answering, and why each matters

**Q1. What URL does a pupil actually land on to sign in?** — **Answered.** Google OAuth 2.0, see "Observed flow" above. `InjectionSpike/Program.cs` line 35 still carries a placeholder default and should be updated once Q2 settles which route wins.

**Q2. Does the email pre-fill actually work?**
This is the entire product. If the pupil's address is not already in the box when the page loads, the app has saved nobody any typing and you are back to a seven-year-old entering 26 characters.

**Q3. What is the window title on the password screen?**
Less obvious, and the reason to do this carefully. Arch §4.2 requires the app to verify it is looking at the right window *before* sending a single keystroke. That check matches on the window title. T0.3 already hit this: the spike originally matched any title containing "Google", which every Chrome window has, and 47 of 50 runs reported a false ready state. **You need the real title, written down exactly.**

## Part 2 — The clean-profile rule

**This is the part people get wrong, and getting it wrong produces a confident false result.**

If you are already signed into Google in your normal browser, the sign-in pages behave completely differently — Google skips the identifier step entirely because it already knows who you are. You will conclude the pre-fill works beautifully when in fact you never tested it.

So every test runs in a **fresh, throwaway Chrome profile**, which is also exactly how the product will launch Chrome (arch §4.4). Step 1.3 below sets up a `New-TestChrome` shortcut that does this for you — use it for every test rather than opening Chrome normally.

When a test window opens it should look freshly installed: no bookmarks, no profile picture, no "Welcome back". **If it looks like your normal browser, stop** — the profile flag did not take effect and every result after that is meaningless.

## Part 3 — The walkthrough

Follow these in order. Steps 1–3 answer whether a pre-fill is possible; step 4 captures the window titles, and **step 4 is the one you must not skip** — it is now the only remaining item that could force a change to arch §4.2.

Budget an hour. Have a text file open to paste into as you go.

---

### Step 1 — Set up

**1.1** Close **every** Chrome window. Check none are hiding in the system tray. This matters for step 4, where you read window titles and stray windows make the list ambiguous.

**1.2** Open PowerShell: press the Windows key, type `powershell`, press Enter.

**1.3** Paste this. It defines a shortcut you will reuse for every test — it launches Chrome in a brand-new empty profile each time, so you are never accidentally testing an already-signed-in session:

```powershell
function New-TestChrome($url) {
  $p = "$env:TEMP\t02-" + (Get-Date -Format "HHmmss")
  & "C:\Program Files\Google\Chrome\Application\chrome.exe" --user-data-dir="$p" --new-window $url
}
```

If Chrome is installed elsewhere, correct the path. To find it: `Get-ChildItem "C:\Program Files*\Google\Chrome\Application\chrome.exe"`.

**1.4** Test the shortcut:

```powershell
New-TestChrome "https://www.google.com"
```

**A window should open that looks freshly installed** — no bookmarks, no profile picture, not signed in. **If it looks like your normal Chrome, stop and fix this before going further.** Every result after this point would otherwise be meaningless.

Close that window.

---

### Step 2 — Find DELIMa's login-start URL

You need the exact address behind the sign-in button, because step 3 attaches a parameter to it.

**2.1** Open the landing page:

```powershell
New-TestChrome "https://d3.delima.edu.my/landing"
```

**2.2** Right-click the sign-in button → **Copy link address**. Paste it into your notes.

**2.3** If "Copy link address" is greyed out, the button is JavaScript rather than a link. Then:

- Press **F12** to open DevTools, click the **Network** tab
- Tick **Preserve log** (important — otherwise the entries vanish on redirect)
- Click the sign-in button
- Look at the **first** request in the list, the one on `d3.delima.edu.my`, and copy its URL from the Headers panel

**Write down:** the login-start URL. It is probably `/landing` itself, or something like `/login`, `/auth/google`, or `/signin`.

Close the window.

### Step 3 — Test whether a pre-fill works

Substitute your own address for `m-12345678@moe-dl.edu.my` everywhere below.

#### Test 3A — Does DELIMa forward `login_hint`?

The best possible outcome. Take the login-start URL from step 2 and add the parameter — use `?` if the URL has no `?` yet, `&` if it already does:

```powershell
New-TestChrome "https://d3.delima.edu.my/landing?login_hint=m-12345678@moe-dl.edu.my"
```

Let the redirects finish, then **click the address bar and copy the whole URL**.

**Look for `login_hint=` in that copied URL.**

- **Present** → DELIMa forwards it. Very good. Now check the page itself: is the email already filled into a password screen?
- **Absent** → DELIMa dropped it. Try `hint=` and `email=` in place of `login_hint=`, since implementations vary. If none survive, this route is out — move to 3B.

**Write down:** which parameter name survived, if any, and whether the email was pre-filled.

Close the window.

#### Test 3B — Account chooser first (only if 3A failed)

Different mechanism: sign into Google *first*, then let DELIMa start its own flow against that signed-in session.

```powershell
New-TestChrome "https://accounts.google.com/AccountChooser?Email=m-12345678@moe-dl.edu.my&hd=moe-dl.edu.my&continue=https://d3.delima.edu.my/landing"
```

Sign in when prompted. **The question is what happens after the password step** — does DELIMa complete on its own, or does it ask you to pick an account again?

**Write down:** whether the email was pre-filled at the Google step, and whether DELIMa completed without further prompting.

Close the window.

#### Test 3C — No pre-fill (only if 3A and 3B both failed)

Confirm the plain flow behaves predictably, since the app will then type the email itself:

```powershell
New-TestChrome "https://d3.delima.edu.my/landing"
```

Click through to the email page. Type the email, press **Enter**.

**Write down:** does Enter advance to the password screen, and roughly how long does it take? Those two facts are what the two-step injection will be built on.

**This is not a failure.** Your app types the email regardless — the hint would have saved a step, not provided the value.

---

### Step 4 — Capture the window titles (do not skip)

Arch §4.2 checks the window title before sending any keystroke. You need a string that appears on the **password screen only**. The spike already lost a run to this: it matched a fragment present in every Chrome window and reported a false ready state in 47 of 50 runs.

**4.1** Get to the sign-in flow again with whichever URL worked best:

```powershell
New-TestChrome "https://d3.delima.edu.my/landing"
```

**4.2** At **each** of the stages below, leave the window open, switch to PowerShell, and run:

```powershell
Get-Process chrome | Where-Object { $_.MainWindowTitle -ne "" } |
  Select-Object -ExpandProperty MainWindowTitle
```

Capture the title at all four stages:

| # | Stage | Title (copy exactly) |
| :-- | :--- | :--- |
| 1 | Page still loading | |
| 2 | Account chooser, if one appears | |
| 3 | **Password field showing** | |
| 4 | Signed in, on DELIMa | |

**Copy them character for character** — including the ` - Google Chrome` suffix and any leading account name. "Roughly what it said" is not usable for a string match.

**4.3** Now compare them and answer one question:

> **Is there any text that appears in row 3 and in none of the others?**

- **Yes** → that string is what arch §4.2 matches on. Write it down. This is the deliverable.
- **No** → a real finding. Window verification needs a different signal — window class, or the tab URL — and **arch §4.2 must be revised before build step 11.** Record all four titles so the decision can be made from evidence.

---

### Step 5 — Timing (optional, 10 minutes)

Only if steps 1–4 went smoothly. `InjectionSpike` already has a mode for this, compiled back at T0.3. From the `InjectionSpike` folder:

```powershell
dotnet run -c Release -- timing --runs 10 --url "THE_URL_THAT_WORKED" --login-hint "m-12345678@moe-dl.edu.my"
```

Put `{0}` where the email belongs in the URL and the harness substitutes it.

**Ten runs, not fifty.** Each is a real sign-in against a real Google account, and fifty in quick succession is how you trigger rate limiting or a security alert.

This gives real numbers for `injection_settle_ms` and `window_wait_timeout_ms` in Appendix B, which are currently 400 ms and 30 s — guesses, not measurements.


If Chrome ever offered to save the password, decline it. The throwaway profiles are gone now either way.

## Part 8 — What each outcome means

| Outcome | What it means | What to do |
| :--- | :--- | :--- |
| **B1 works** — `login_hint` passes through, password field pre-filled | Best case. One injection, no picker. | Record the URL, unblock Prompt 11 |
| **B2 works** — chooser signs in, DELIMa completes on its own | Good. One extra page, still one password injection. | Record it; note the extra step in the pupil guide |
| **B3 only** — no pre-fill available | Acceptable. Two injections, both proven at T0.3. | Build §4.2's engine for a two-step sequence |
| Account picker appears despite `hd` | One extra pupil click; does not break the product | Record it; the pupil-facing guide must show that screen |
| An invented `state` appears to work | DELIMa is not validating CSRF state | **Do not build on it.** Report to BSTP; use B1/B2/B3 |
| No unique password-screen window title | Window verification needs another signal | Record all titles; arch §4.2 needs revising before step 11 |

**`DELIMa does not use Google sign-in` has been removed from this table — it was the outcome that would have forced a respec, and the August 2026 observation ruled it out.**

**The window-title row is now the one carrying real risk.** It would otherwise surface midway through building the injection flow, which is the most delicate code in the product.

**Design for route C regardless of what passes.** Even if B1 works today, Google changes these flows without notice, and an engine that can only handle a pre-filled email will break on the day it stops being pre-filled. Two-step capability is the resilient design, not the fallback.

## A note on doing this safely

You are typing a real password into a real sign-in page, which is ordinary. Two things to keep ordinary:

- **Do not save the password in Chrome.** Decline the prompt. The throwaway profiles are deleted afterwards anyway, but decline it regardless.
- **Do not run these tests on a pupil's account without the school's knowledge.** Your own account, or an account created for testing, avoids the question entirely.

Nothing in T0.2 stores a credential, and nothing here engages the T0.1 question — this is an ordinary sign-in, not storage or replay.
