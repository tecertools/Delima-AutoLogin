## Observed flow — August 2026

Captured by walking the live portal. Session-bound values (`state`, `dsh`, `as`, `part`) are deliberately replaced with placeholders here — they are single-use and expired, but this repository is public and there is no reason to publish session tokens.

**1. Landing**

```
https://d3.delima.edu.my/landing
```

**2. Redirects into a Google OAuth 2.0 authorization-code flow**, with DELIMa's own OAuth client:

```
https://accounts.google.com/v3/signin/accountchooser
  ?client_id=950472034074-acj262jqk6trve8i4ndsudqeokvh5pef.apps.googleusercontent.com
  &redirect_uri=https%3A%2F%2Fd3.delima.edu.my%2Fauthentication%2Fcode
  &response_type=code
  &scope=openid+email+profile
  &state=<server-generated, validated on callback>
  &dsh=<session>  &o2v=2  &service=lso  &flowName=GeneralOAuthFlow
  &app_domain=https%3A%2F%2Fd3.delima.edu.my
```

**3. Then the identifier (email) page**, carrying the same parameters:

```
https://accounts.google.com/v3/signin/identifier?...same client_id, state, dsh...
```

### What this settles

- **Q1 is answered. It is Google OAuth 2.0.** Arch §4.5's core assumption holds — this is not a proprietary identity provider, and the section does not need re-specifying at the root.
- **DELIMa runs its own Google Cloud project.** The `client_id` above is DELIMa's. **No school Cloud project is needed**, which removes the cost that made the `login_hint` route look expensive. A `client_id` is not a secret; it is visible to every user in every authorize URL. DELIMa's *client secret* is a different matter and must never appear here.
- **`state` blocks the obvious approach.** It is generated per session by DELIMa and validated when Google calls back. The launcher cannot mint its own authorize URL with `login_hint` appended — an invented `state` fails validation, leaving the pupil signed into Google but not into DELIMa.

### What is still open

Q2 (does a pre-fill work) and Q3 (the password-screen window title) are unanswered. The three candidate routes are in arch §4.5; Part 4 below is now narrowed to testing them in order.

This is a browser test. No code is written. You are answering three questions that the rest of the injection flow is built on top of, and getting them wrong means rebuilding step 11.

**Q1. What URL does a pupil actually land on to sign in?**

## Part 2 — The clean-profile rule

**This is the part people get wrong, and getting it wrong produces a confident false result.**

If you are already signed into Google in your normal browser, the sign-in pages behave completely differently — Google skips the identifier step entirely because it already knows who you are. You will conclude the pre-fill works beautifully when in fact you never tested it.

So every test below runs in a **fresh, throwaway Chrome profile**, which is also exactly how the product will launch Chrome (arch §4.4).

Open PowerShell and use this to launch Chrome for each test:

```powershell
$profile = "$env:TEMP\t02-" + (Get-Date -Format "HHmmss")
& "C:\Program Files\Google\Chrome\Application\chrome.exe" --user-data-dir="$profile" --new-window "URL_GOES_HERE"
```

A brand-new profile each time, because the timestamp changes. When Chrome opens it should look freshly installed — no bookmarks, no signed-in account, no "Welcome back".

**If it looks like your normal browser, stop.** The profile flag did not take effect and every result after that is meaningless.

Delete them when you are finished:

```powershell
Remove-Item "$env:TEMP\t02-*" -Recurse -Force
```

## Part 4 — Test B: does the pre-fill work?

Three routes, in this order. Stop at the first that works end to end — meaning **signed into DELIMa**, not merely signed into Google.

### B1 — Does DELIMa pass `login_hint` through? (try this first)

Many OpenID Connect clients forward `login_hint` from their own login-start URL into the authorize request. If DELIMa does, this is the cleanest possible answer: one injection, no account picker.

First find the real login-start URL. On `/landing`, right-click the sign-in button → **Copy link address**. It may be `/landing` itself, or something like `/login` or `/auth/google`.

Then try, in a fresh profile:

```
https://d3.delima.edu.my/landing?login_hint=m-12345678@moe-dl.edu.my
```

Watch the address bar as it redirects. **Success looks like `login_hint=` appearing in the Google authorize URL**, and landing on a password field with the email already filled.

If the parameter is silently dropped, it is not supported. Try `hint=` and `email=` as well — implementations vary — then move on.

### B2 — Account chooser first, then let DELIMa start its own flow

Not a hijack of DELIMa's OAuth flow, which `state` prevents. Instead: sign into Google *first*, then visit DELIMa and let it run its own flow against the now-signed-in session.

```
https://accounts.google.com/AccountChooser?Email=m-12345678@moe-dl.edu.my&hd=moe-dl.edu.my&continue=https://d3.delima.edu.my/landing
```

**The question is what happens after the Google password step.** DELIMa should start its own OAuth flow, find exactly one signed-in matching account, and complete without further prompting. Record whether it does, or whether an account chooser still appears.

### B3 — No pre-fill: inject the email too

If B1 and B2 both fail, the launcher lands on the identifier page and types the email, presses Enter, then types the password. **This is an acceptable outcome**, not a failure — this application types the email itself, so the hint saves a step rather than providing the value. T0.3 proved both injections work.

If you get here, record how the identifier page behaves: does Enter advance to the password screen, and how long does that take? Those numbers feed arch §4.2.

## Part 5 — Test C: capture the exact window title

Get to the password screen using whichever URL worked. **Leave it open**, and in PowerShell run:

```powershell
Get-Process chrome | Where-Object { $_.MainWindowTitle -ne "" } |
  Select-Object Id, MainWindowTitle | Format-List
```

**Copy the title exactly** — every character, including the ` - Google Chrome` suffix and any leading account name.

Then do it again at each stage and record all of them:

- while the page is still loading
- at the account-chooser step, if one appeared
- at the password field
- after signing in, on the DELIMa page

**Why this matters more than it looks.** Arch §4.2 verifies the window before sending keystrokes, and §4.3's failure taxonomy depends on telling these states apart. The spike's original bug was matching a title fragment that was present in *all* of them. What you want to identify is a string that appears **only** on the password screen. If no such string exists, say so — that is a real finding, and it means window verification needs another signal such as the window class or the tab URL.

## Part 6 — Test D: timing (optional, but the tool already exists)

`InjectionSpike` has a `timing` mode built for exactly this, and it is already compiled from T0.3. From the `InjectionSpike` folder:

```powershell
dotnet run -c Release -- timing --runs 10 --url "PASTE_THE_WORKING_URL_HERE" --login-hint "m-12345678@moe-dl.edu.my"
```

Put `{0}` where the email goes in the URL and the harness substitutes it for you.

This measures how long the password field takes to become ready, across ten runs. It matters because `injection_settle_ms` and `window_wait_timeout_ms` in Appendix B are currently defaults picked without data — 400 ms and 30 s. Ten runs on a real lab PC on real school internet will tell you whether those are sensible.

**Use ten runs, not fifty.** Each one is a real sign-in attempt against a real Google account, and fifty in quick succession is the kind of thing that trips rate limiting or a security alert on the account.

## Part 8 — What each outcome means

| Outcome | What it means | What to do |
| :--- | :--- | :--- |
| **B1 works** — `login_hint` passes through, password field pre-filled | Best case. One injection, no picker. | Record the URL, unblock Prompt 11 |
| **B2 works** — chooser signs in, DELIMa completes on its own | Good. One extra page, still one password injection. | Record it; note the extra step in the pupil guide |
| **B3 only** — no pre-fill available | Acceptable. Two injections, both proven at T0.3. | Build §4.2's engine for a two-step sequence |
| Account picker appears despite `hd` | One extra pupil click; does not break the product | Record it; the pupil-facing guide must show that screen |
| An invented `state` appears to work | DELIMa is not validating CSRF state | **Do not build on it.** Report to BSTP; use B1/B2/B3 |
| No unique password-screen window title | Window verification needs another signal | Record all titles; arch §4.2 needs revising before step 11 |

**`DELIMa does not use Google sign-in` has been removed from this table — it was the outcome that would have forced a respec, and the August 2026 observation ruled it out.**

**The window-title row is now the one carrying real risk.** It would otherwise surface midway through building the injection flow, which is the most delicate code in the product.

**Design for route C regardless of what passes.** Even if B1 works today, Google changes these flows without notice, and an engine that can only handle a pre-filled email will break on the day it stops being pre-filled. Two-step capability is the resilient design, not the fallback.

## A note on doing this safely

You are typing a real password into a real sign-in page, which is ordinary. Two things to keep ordinary:

- **Do not save the password in Chrome.** Decline the prompt. The throwaway profiles are deleted afterwards anyway, but decline it regardless.
- **Do not run these tests on a pupil's account without the school's knowledge.** Your own account, or an account created for testing, avoids the question entirely.

Nothing in T0.2 stores a credential, and nothing here engages the T0.1 question — this is an ordinary sign-in, not storage or replay.
