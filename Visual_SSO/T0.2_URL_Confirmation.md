**Status:** Not started
**Time:** about an hour
**Needs:** one working DELIMa account, a Windows PC with Chrome, and somewhere private to work
**Blocks:** build step 11 (the injection flow) and Prompt 11 in `Build_Prompts.md`

This is a browser test. No code is written. You are answering three questions that the rest of the injection flow is built on top of, and getting them wrong means rebuilding step 11.

## Part 0 — What you are answering, and why each matters

**Q1. What URL does a pupil actually land on to sign in?**
`Technical_Architecture_Visual_SSO.md` §4.5 carries two candidates and says to resolve them against the live portal. Right now the code has a placeholder — `InjectionSpike/Program.cs` line 35 — with a comment saying so.

**Q2. Does the email pre-fill actually work?**
This is the entire product. If the pupil's address is not already in the box when the page loads, the app has saved nobody any typing and you are back to a seven-year-old entering 26 characters.

**Q3. What is the window title on the password screen?**
Less obvious, and the reason to do this carefully. Arch §4.2 requires the app to verify it is looking at the right window *before* sending a single keystroke. That check matches on the window title. T0.3 already hit this: the spike originally matched any title containing "Google", which every Chrome window has, and 47 of 50 runs reported a false ready state. **You need the real title, written down exactly.**

## Part 1 — Before you start

**Use an account you control.** Your own teacher account, or a test pupil account created for this. You need to know the password and be willing to type it.

**Do not use a lab PC that other people use**, and do not let the browser save the password. The clean-profile method below handles this, but do not defeat it by clicking "Save password" when Chrome asks.

**Have somewhere to write results.** A text file. You will be recording exact URLs and exact window titles, and "roughly what it said" is not good enough for a string match.

## Part 2 — The clean-profile rule

**This is the part people get wrong, and getting it wrong produces a confident false result.**

If you are already signed into Google in your normal browser, the sign-in pages behave completely differently — Google skips the identifier step entirely because it already knows who you are. You will conclude the pre-fill works beautifully when in fact you never tested it.

So every test below runs in a **fresh, throwaway Chrome profile**, which is also exactly how the product will launch Chrome (arch §4.4).

Open PowerShell and use this to launch Chrome for each test:

```powershell
$profile = "$env:TEMP\t02-" + (Get-Date -Format "HHmmss")
& "C:\Program Files\Google\Chrome\Application\chrome.exe" --user-data-dir="$profile" --new-window "URL_GOES_HERE"
```

A brand-new profile each time, because the timestamp changes. When Chrome opens it should look freshly installed — no bookmarks, no signed-in account, no "Welcome back".

**If it looks like your normal browser, stop.** The profile flag did not take effect and every result after that is meaningless.

Delete them when you are finished:

```powershell
Remove-Item "$env:TEMP\t02-*" -Recurse -Force
```

## Part 3 — Test A: what the portal does on its own

Launch a clean profile at the portal with no hints at all:

```
https://d3.delima.edu.my
```

**Record:**

1. Every URL you are redirected through — click the address bar and copy the full text at each stop. Redirects are where the real entry point hides.
2. Where you finally land. Is it a Google sign-in page? A DELIMa-branded page? A Microsoft one?
3. Whether the address bar shows `accounts.google.com` at any point.

Sign in normally, by hand, and note whether anything unexpected happens — a consent screen, a two-step prompt, a domain picker.

**What this tells you:** whether the sign-in is Google-backed at all. Everything in §4.5 assumes it is. If it turns out DELIMa uses its own identity provider, both candidate URLs are wrong and this needs re-specifying before any code is written.

## Part 4 — Test B: does the pre-fill work?

The candidate from arch §4.5, the one `Normal_SSO` uses today. Substitute your real address and take care with the `continue` value:

```
https://accounts.google.com/AccountChooser?Email=m-12345678@moe-dl.edu.my&hd=moe-dl.edu.my&continue=https://d3.delima.edu.my
```

Launch it in a **fresh** profile.

**Record, precisely:**

| Question | What to write down |
| :--- | :--- |
| Did it go straight to a password field? | Yes / No |
| Was the email already filled in? | Yes / No — and if yes, exactly as typed, or reformatted? |
| Was the email shown but greyed out, or editable? | Which |
| Did an account picker appear first? | Yes / No |
| After signing in, did you land on DELIMa? | Yes / No — or where instead |
| How long from launch to the password field being usable? | Seconds, roughly |

**If the email is pre-filled and you land on DELIMa: T0.2 passes**, and the URL you just used is the answer. Record it exactly.

**If the email is not pre-filled**, try the same URL without the `continue` parameter, then without `hd`. Narrowing which parameter breaks it is useful information either way.

**Skip the OAuth `login_hint` candidate for now.** Arch §4.5 notes it needs a school Google Cloud project, which is a significant piece of setup. Only go there if Test B fails — and if it does, that is a finding worth recording before spending days on Cloud configuration.

## Part 5 — Test C: capture the exact window title

Get to the password screen using whichever URL worked. **Leave it open**, and in PowerShell run:

```powershell
Get-Process chrome | Where-Object { $_.MainWindowTitle -ne "" } |
  Select-Object Id, MainWindowTitle | Format-List
```

**Copy the title exactly** — every character, including the ` - Google Chrome` suffix and any leading account name.

Then do it again at each stage and record all of them:

- while the page is still loading
- at the account-chooser step, if one appeared
- at the password field
- after signing in, on the DELIMa page

**Why this matters more than it looks.** Arch §4.2 verifies the window before sending keystrokes, and §4.3's failure taxonomy depends on telling these states apart. The spike's original bug was matching a title fragment that was present in *all* of them. What you want to identify is a string that appears **only** on the password screen. If no such string exists, say so — that is a real finding, and it means window verification needs another signal such as the window class or the tab URL.

## Part 6 — Test D: timing (optional, but the tool already exists)

`InjectionSpike` has a `timing` mode built for exactly this, and it is already compiled from T0.3. From the `InjectionSpike` folder:

```powershell
dotnet run -c Release -- timing --runs 10 --url "PASTE_THE_WORKING_URL_HERE" --login-hint "m-12345678@moe-dl.edu.my"
```

Put `{0}` where the email goes in the URL and the harness substitutes it for you.

This measures how long the password field takes to become ready, across ten runs. It matters because `injection_settle_ms` and `window_wait_timeout_ms` in Appendix B are currently defaults picked without data — 400 ms and 30 s. Ten runs on a real lab PC on real school internet will tell you whether those are sensible.

**Use ten runs, not fifty.** Each one is a real sign-in attempt against a real Google account, and fifty in quick succession is the kind of thing that trips rate limiting or a security alert on the account.

## Part 8 — What each outcome means

| Outcome | What it means | What to do |
| :--- | :--- | :--- |
| Pre-fill works, lands on DELIMa | **T0.2 passes.** Best case. | Record the URL, unblock Prompt 11 |
| Pre-fill works, `continue` ignored — lands on Google, signed in | Acceptable. `Normal_SSO` §5.5 anticipated this. | Ship it; a lab bookmark to DELIMa covers the gap |
| Account picker appears despite `hd` | Adds one pupil click, does not break the product | Record it; the pupil-facing guide needs to show that screen |
| Email not pre-filled at all | The core benefit is gone via this route | Try the OAuth `login_hint` route (§4.5), which needs a school Cloud project |
| DELIMa does not use Google sign-in | §4.5 is wrong at the root | **Stop and re-specify.** Do not build step 11 against a guess |
| No unique password-screen window title | Window verification needs another signal | Record all titles; arch §4.2 needs revising before step 11 |

**The last two rows are why this is worth an hour now.** Both would otherwise be discovered midway through building the injection flow, which is the most delicate code in the product.

## A note on doing this safely

You are typing a real password into a real sign-in page, which is ordinary. Two things to keep ordinary:

- **Do not save the password in Chrome.** Decline the prompt. The throwaway profiles are deleted afterwards anyway, but decline it regardless.
- **Do not run these tests on a pupil's account without the school's knowledge.** Your own account, or an account created for testing, avoids the question entirely.

Nothing in T0.2 stores a credential, and nothing here engages the T0.1 question — this is an ordinary sign-in, not storage or replay.
