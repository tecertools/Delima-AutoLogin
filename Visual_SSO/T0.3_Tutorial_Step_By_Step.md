# T0.3 — Step-by-Step Tutorial

**For someone who has not done this before.** Every command is written out in full. Nothing is assumed.

**Companion:** `T0.3_Injection_Test_Protocol.md` — the short version, once you have done this once.

**Total time:** about 1 hour at home, about 2 hours in the lab.

---

## Part 0 — What you are actually doing, in plain words

Your planned app needs to type a pupil's password into Chrome for them. Windows offers two ways to fake a keystroke, and the original plan picked the wrong one.

- **`SendKeys`** — the old, easy way. It has a catch: it treats `+ ^ % ~ ( ) { } [ ]` as *instructions*, not letters. `+a` means "hold Shift and press A". So a password like `Murid+2026` gets typed as something else entirely, and nobody can see why.
- **`SendInput`** — the harder, correct way. It sends each character as a raw character, so symbols arrive as symbols.

The test program launches Chrome at a small local web page with a password box, types a test password into it using one method or the other, and the page reports whether the characters arrived intact.

**You are running an experiment to see one method fail and the other succeed.** That is the whole idea. If both succeed, or both fail, that is a surprise and you stop.

There is a second question the program also answers: **how long does Chrome take to be ready?** The original plan assumed 1.5 seconds. If the true answer is 5 seconds, then the app would be typing a child's password 3.5 seconds before Chrome is listening — into whatever window happens to be in front. That is the failure that matters most.

### Words you will see

| Word | Means |
| :--- | :--- |
| **Terminal / PowerShell** | A window where you type commands instead of clicking. |
| **SDK** | The toolkit that turns C# source code into a running program. You need the SDK, not just the "Runtime". |
| **Build** | Turning the source code into a program. |
| **Publish** | Building it *and* packing everything it needs into one folder you can copy to another PC. |
| **Argument / flag** | Extra words after a command that change what it does, like `--runs 50`. |
| **CSV** | A spreadsheet file. The program writes your results into one. |
| **Working directory** | The folder your terminal is "standing in". Files get written here. |

## Part 1 — What you need

**At home, on your own Windows PC:**

- Windows 10 or 11
- Google Chrome installed
- About 2 GB of free disk space
- Internet (to download the toolkit)
- A USB stick, 1 GB or larger

**At the school:**

- A lab PC that is **typical** — if 30 PCs are old and 2 are new, test an old one. The old ones are where this breaks.
- Permission to sit at it uninterrupted for about 2 hours
- Permission to plug in a USB stick and run a program from it (**check this in advance** — see Part 10, "The lab PC blocks it")

> **You will not install anything on the school PC.** Part 5 packs the test into a folder that runs on its own. This matters, because school PCs are usually locked down and a novice discovering that at 9 a.m. in a lab loses the whole session.

## Part 2 — Install the toolkit (at home, ~10 minutes)

### 2.1 Get the .NET 10 SDK

1. Open <https://dotnet.microsoft.com/download/dotnet/10.0> in your browser.
2. Find the **SDK** column — not "Runtime", not "Desktop Runtime". You need the SDK.
3. Under **Windows**, click **x64**.
4. Run the downloaded installer. Click through the defaults.

> **Why .NET 10, not .NET 8.** The test was originally written against .NET 8. .NET 8 stops receiving security updates on **10 November 2026** — a few months from now — so both the test and the real app target **.NET 10** instead, which is LTS (Long Term Support) and covered until November 2028. The project's `.csproj` file already specifies `net10.0-windows`, so you just need the matching SDK installed.

### 2.2 Check it worked

1. Press the **Windows key**, type `powershell`, and press **Enter**. A blue window opens.
2. Type this exactly and press Enter:

```powershell
dotnet --version
```

**Good:** something like `10.0.100`.

**Bad:** *"dotnet is not recognized..."* → **close the PowerShell window and open a new one.** The installer changes a setting that only new windows pick up. If it still fails after that, restart the PC.

## Part 3 — Build the test program (at home, ~5 minutes)

### 3.1 Point PowerShell at the right folder

The test lives in the `InjectionSpike` folder inside your project. In PowerShell, type `cd`, then a space, then **drag the `InjectionSpike` folder from File Explorer into the PowerShell window** — it fills in the path for you, quotes and all. Then press Enter.

It will look something like:

```powershell
cd "C:\Delima-AutoLogin\InjectionSpike"
```

> **Why the quotes matter:** if your folder path has spaces in it, quotes prevent PowerShell from misinterpreting parts of the path. Dragging the folder always gets this right.

**Now confirm you actually landed there — do not skip this.** Two checks:

```powershell
Get-Location
```

```powershell
dir *.csproj, *.sln
```

The first prints where you are standing. The second prints exactly what the build tool will see.

| What the second command shows | Meaning |
| :--- | :--- |
| **Exactly one file**, `InjectionSpike.csproj` | Correct. Continue. |
| Nothing at all | You are not in the `InjectionSpike` folder. Redo the `cd`. |
| **Two or more files** | You are in some other folder that happens to contain projects. Redo the `cd`, or use the bulletproof method in 3.3. |

This check exists because the most common first error is caused entirely by standing in the wrong folder, and the error message does not say so.

### 3.3 The bulletproof alternative — name the project file

If the `cd` keeps going wrong, stop fighting it. You can tell `dotnet` exactly which project to build, and then **it does not matter which folder you are standing in.**

Type `dotnet build`, then a space, then **drag `InjectionSpike.csproj` itself — the file, not the folder** — from File Explorer into the PowerShell window. It fills in the full path with quotes. Then type ` -c Release` and press Enter.

```powershell
dotnet build "C:\Delima-AutoLogin\InjectionSpike\InjectionSpike.csproj" -c Release
```

The same applies to the later commands. Note that `dotnet run` needs the word `--project` first, and still needs the `--` before the test's own arguments:

```powershell
dotnet run --project "C:\...\InjectionSpike\InjectionSpike.csproj" -c Release -- fidelity --method sendinput --runs 3
```

```powershell
dotnet publish "C:\...\InjectionSpike\InjectionSpike.csproj" -c Release -r win-x64 --self-contained true -o "C:\Users\King\Desktop\T03-test"
```

Giving `-o` a full path (rather than just `publish`) means the output folder lands somewhere you can find, instead of wherever PowerShell happened to be standing.

### 3.2 Build it

Only once `dir *.csproj, *.sln` above showed exactly one file:

```powershell
dotnet build -c Release
```

The first run downloads some pieces and takes a minute or two. Later runs take seconds.

**Good:** ends with `Build succeeded.` and `0 Error(s)`. Warnings are fine — ignore them.

**Bad:** a list of errors. **Do not panic, and do not start editing code.** This program has never been compiled before, so a few small errors are expected. Copy the whole error text and bring it to me — these are almost always one-line fixes. See Part 10 for the two most likely ones.

## Part 4 — A tiny practice run (at home, ~2 minutes)

Never let the lab be the first time you see this run.

**Before you start:** close every other window except PowerShell. Chrome is about to open and steal your keyboard.

```powershell
dotnet run -c Release -- fidelity --method sendinput --runs 3
```

> **Why `--` in the middle?** It separates arguments for the `dotnet` tool from arguments for *your* program. Everything after `--` gets handed to the test. Forget it and you get a confusing error.

**What you will see happen:** Chrome opens three times, briefly, each time flashing a page with a password box. Your mouse and keyboard will feel frozen for a second each time — that is `BlockInput`, and it is deliberate. Do not touch anything.

**Good output:**

```
Chrome: C:\Program Files\Google\Chrome\Application\chrome.exe

MODE A — fidelity   method=sendinput   runs=3   settle=400ms   char-delay=0ms
------------------------------------------------------------------------------
    1. plain-lower        PASS  ready= 1840ms
    2. plain-lower        PASS  ready= 1290ms
    3. plain-lower        PASS  ready= 1310ms

SUMMARY BY PASSWORD
------------------------------------------------------------------------------
  plain-lower          3/3   passed

CSV: C:\...\InjectionSpike\fidelity_sendinput_d0_20260817_143022.csv

VERDICT: all characters survived injection.
```

Three PASSes means the machinery works. **It tells you nothing about whether the approach is viable** — that needs the full run, on lab hardware, with the symbol passwords.

If you see `WINDOW_NOT_READY`, jump to Part 10.

## Part 5 — Pack it for the lab (at home, ~5 minutes)

This builds a version that carries its own copy of .NET, so the school PC needs nothing installed.

```powershell
dotnet publish -c Release -r win-x64 --self-contained true -o publish
```

Takes a minute and produces a `publish` folder of roughly 150 MB. Check it contains `InjectionSpike.exe` **and** `testpage.html`:

```powershell
dir publish\InjectionSpike.exe, publish\testpage.html
```

Both must be listed. Without `testpage.html` the test cannot run.

**Copy the whole `publish` folder to your USB stick.** Rename it something obvious like `T03-test`.

Also put on the stick: a printout of `T0.3_Injection_Test_Protocol.md`, and the results table from Part 9 below.

## Part 6 — One question to ask before you go

Ask the ICT coordinator: **"What do the DELIMa passwords look like — how long, and do they contain symbols?"**

Ask for the *pattern*. Never ask for actual passwords, and never type a real password into this test.

Why this matters: the test uses invented passwords full of symbols. If real MOE passwords turn out to be plain like `Murid1234`, then the symbol problem never occurs at your school, half this test is answering a question you do not have, and you should know that before designing warnings around it. If they *do* contain symbols, this test is the most important hour of the project.

## Part 7 — At the lab: before you touch anything

### 7.1 Write down the machine

You cannot generalise a result you cannot describe. Record:

| | |
| :--- | :--- |
| PC make and model | |
| **Hard disk: spinning (HDD) or solid-state (SSD)?** | |
| RAM | |
| Windows version | |
| Chrome version | |
| Wired or Wi-Fi | |

To find the disk type: press Windows key, type `defrag`, open **Defragment and Optimise Drives**. The "Media type" column says **Hard disk drive** or **Solid state drive**. This is the single biggest factor in your timing results.

Chrome version: open Chrome → three dots → Help → About Google Chrome.

### 7.2 Safety rules

1. **Close everything.** No Word, no browser with a form open, no email. If something goes wrong, keystrokes go wherever the focus is.
2. **Close your own Chrome.** You will check at the end that it survived — that is part of the test.
3. **Close every Chrome window before you start, including ones left over from an earlier attempt.** If a previous run was interrupted — a build failure, a Ctrl+C, closing PowerShell mid-run — its Chrome window can still be open in the background. The test now closes these automatically at the start of each run and prints `Closed N leftover SPIKE window(s)` if it found any, but check by eye too: press **Alt+Tab** and confirm nothing unexpected is sitting there. A leftover window was the cause of one real session's results looking erratic — several runs timing out and one taking 15 seconds instead of the usual 0.7.
4. **Sit at the machine.** Not Remote Desktop. The test drives the real keyboard and behaves differently over RDP.
5. **Do not leave the desk during a run.** If your keyboard and the test's keystrokes interleave, the results are meaningless.
6. **Do not touch the mouse or keyboard while a run is in progress.**

### 7.3 Open PowerShell on the lab PC

Plug in the USB. Find the drive letter in File Explorer (often `E:` or `D:`).

Press Windows key → type `powershell` → Enter. Then:

```powershell
cd E:\T03-test
```

Replace `E:` with your actual drive letter.

> **Windows may block the program** because it came from a USB and is unsigned. See Part 10, "Windows protected your PC". Sort this out now, not mid-test.

**Note:** on the lab PC you run `.\InjectionSpike.exe` directly — there is no `dotnet run` and no `--` separator, because .NET is not installed there.

## Part 8 — The five tests, in order

### Test 1 — `sendkeys`, the control (~8 minutes)

**Run this first.** It is the one that proves the problem exists. If you run the good method first and it works, you will be tempted to skip this — and then you have no evidence for the decision the whole project rests on.

```powershell
.\InjectionSpike.exe fidelity --method sendkeys --runs 50
```

**Expected — and "failures" here are the correct result:**

```
  plain-lower          5/5   passed
  plain-mixed          5/5   passed
  plus                 0/5   passed   <-- CORRUPTED
  caret                0/5   passed   <-- CORRUPTED
  percent              0/5   passed   <-- CORRUPTED
  all-reserved         0/5   passed   <-- CORRUPTED
```

Plain passwords survive; symbol passwords are destroyed. **That is the finding.** It means the original plan would have silently broken every pupil whose password contains a symbol, with no error message and no way to diagnose it.

### Test 2 — `sendinput`, the candidate (~8 minutes)

```powershell
.\InjectionSpike.exe fidelity --method sendinput --runs 50
```

**Expected:** every row passes, including all the symbol ones.

**If some rows fail**, do not conclude the method is broken. Try slowing it down:

```powershell
.\InjectionSpike.exe fidelity --method sendinput --runs 20 --char-delay 15
```

This puts a 15-millisecond gap between characters. If that fixes it, the problem was *dropped* characters (a speed issue, easily fixed) rather than *corrupted* ones (a dead approach). These look identical in the summary and mean completely different things.

If it fails at both settings — **stop. Keep the CSV files. Do not build anything else.**

### Test 3 — Cold-start timing (~30 minutes, mostly waiting)

This is the test most easily done wrong, and the one that kills the original 1.5-second assumption.

**Do this exactly:**

1. Restart the PC.
2. Log in. **Wait 2 minutes** for the disk to stop working — watch the disk activity light, or Task Manager's Disk column settle near 0%.
3. Open PowerShell, `cd` to your folder.
4. Run **exactly one**:

```powershell
.\InjectionSpike.exe timing --runs 1
```

5. Write down the `ready=` number.
6. **Repeat from step 1, five times total.**

**Why the tedium:** after Chrome launches once, Windows keeps its files in memory, so every later launch is much faster. The situation you care about is the *first pupil of the day on a cold machine* — and the normal 50-run loop measures that exactly once and then averages it away. These five reboots are your only honest cold-start numbers.

This test opens Google's page but **sends no keystrokes and needs no account.**

### Test 4 — Warm timing (~12 minutes)

Straight after Test 3's last reboot:

```powershell
.\InjectionSpike.exe timing --runs 50
```

**Expected output at the end:**

```
  window-ready p50 :   2840 ms
  window-ready p95 :   6120 ms
  window-ready max :   9450 ms

  runs exceeding the PRD's 1,500 ms assumption: 47/50 (94%)
```

That last line is the important one. Read it as: *"in 94% of launches, the original design would have typed a child's password into the wrong window."* Write the number down — it is the argument you will show whoever signs this off.

> `p50` means half the runs were faster than this. `p95` means 95% were faster — the "bad but not rare" case.

### Test 5 — The focus-steal test (~10 minutes, manual)

Tests 1–4 prove injection *works*. This proves it **refuses to work when it shouldn't** — the thing standing between a child's password and the URL bar. It is the most important test here and the program cannot do it for you.

1. Open **Notepad**. Type nothing. Leave it visible next to PowerShell.
2. Start a run:

```powershell
.\InjectionSpike.exe fidelity --method sendinput --runs 1
```

3. **As soon as Chrome starts opening, click on the Notepad window** to steal the focus.
4. Wait for the run to finish.
5. **Look at Notepad.**

| Result | Meaning |
| :--- | :--- |
| Notepad is **empty**, run says `WINDOW_NOT_READY` | **PASS.** The program checked its target, did not find it, and typed nothing. Correct. |
| **Any characters** appear in Notepad | **FAIL. Stop the project here.** The program will type children's passwords into random windows. Nothing else matters until this is fixed. |

**Repeat 5 times**, clicking Notepad at different moments — instantly, after ~1 second, ~2 seconds, ~4 seconds. You need **5 out of 5 empty**.

### After all five — three final checks

1. **Open Chrome.** Did your own Chrome survive, and does it *not* say "Restore pages?" That proves the teardown only killed its own Chrome, not the teacher's.
2. Press Windows+R, type `%TEMP%`, Enter. Search for `delima_spike`. **There should be nothing** — the test cleans up after itself.
3. Copy every `.csv` file from the test folder onto your USB stick.

## Part 10 — When something goes wrong

### "dotnet is not recognized"
Close PowerShell, open a new one. The installer's changes only apply to new windows. Still failing? Restart the PC.

### "MSB1011: Specify which project or solution file to use because this folder contains more than one"
**You are in the wrong folder.** The `InjectionSpike` folder contains exactly one project file, so this error cannot come from it — you are standing somewhere else that happens to contain several.

This is a location problem, not a code problem. Nothing is broken.

```powershell
Get-Location
dir *.csproj, *.sln
```

If the second command lists more than one file, redo the `cd` from step 3.1 — or skip the whole issue by naming the project file explicitly, as in step 3.3.

### "MSB1003: Specify a project or solution file. The current working directory does not contain one"
The mirror image of the above: you are in a folder with **no** project at all — often the repository root, or your user folder if the `cd` never ran. Same two checks, same fix.

### The build shows errors
This means the build actually started, so your folder is right. Errors here are expected — this code has never been compiled. **Do not start editing it.** Copy the full error text and bring it to me. The two most likely:

- *"The type or namespace name 'Registry' does not exist"* → needs one package added.
- *"SendKeys does not exist in the current context"* → the WinForms setting is not being picked up.

Both are one-line fixes.

### "Windows protected your PC" (blue box)
Expected. The program is unsigned and came from a USB. Click **More info** → **Run anyway**.

If it keeps happening, unblock the files first:

```powershell
Get-ChildItem -Recurse | Unblock-File
```

### Antivirus deletes or quarantines the program
Also expected, and reasonable — this program types keystrokes into other windows, which is exactly what a keylogger does. **Talk to the ICT coordinator before your lab session** and get the folder allow-listed. Do not disable the antivirus.

This is worth noticing: if antivirus objects to the *test*, it will object to the *real app*, on all 40 PCs. That is a genuine deployment problem and better discovered now.

### "FATAL: chrome.exe not found"
Chrome is not installed, or is installed somewhere unusual. Install Chrome, or note the path — the fact that the program could not find it is itself a finding worth recording.

### Every run says `WINDOW_NOT_READY`
The program launched Chrome but never saw the window it expected.

- Is Chrome actually opening? Watch the screen during a run.
- Did you click something during the run? Start over and keep your hands off.
- Very slow PC? Chrome may need longer than the 30-second limit — unlikely, but note it.

### The run says `blockinput_denied`
The program could not freeze your keyboard. **This is a finding, not an error** — write it down. Do **not** fix it by running as administrator, because the real app will not run as administrator either. Just be extra careful not to touch anything during runs.

### My keyboard and mouse froze
That is `BlockInput` working correctly. It releases when the run finishes. If a run crashes while input is blocked, press **Ctrl+Alt+Delete** — that always works — then Escape.

### I cannot run anything from USB on the school PC
The lab has execution restrictions. Two options: ask ICT to allow it temporarily, or copy the folder to the PC's `Desktop` first and run it from there.

Worth noticing again: this restriction is *good* — it is one of the controls the real app depends on. Find out exactly what it is; it goes in the deployment guide.
